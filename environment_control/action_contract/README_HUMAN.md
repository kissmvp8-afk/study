## 学习目标与必要概念

在机器人强化学习中，算法大脑在每一个控制周期都会输出一串数字。比如：`[0, 0, 0, 0.4, 0, 0, 0, 0]`。
这 8 个数字究竟代表什么？哪个数字控制抬腿，哪个数字控制转轮子？如果策略大脑输出一个 `0.4`，电机是应该转动 0.4 度、0.4 弧度，还是以每秒 0.4 米的速度向前冲？

如果控制代码和学习算法对这 8 个数字的理解不一致，机器人就会立刻失控摔倒。**E03 模块的核心使命，就是为这 8 个数字立下一份不可动摇的“动作契约（定义表）”**：为每一个数字明确登记它绑定哪个关节、控制什么物理量、基准默认值是多少、放大系数是多少，以及如何一步步换算成真实的电机物理目标。

本篇保留动作术语和数值例子，具有 Python 基础的读者可沿着“配置文件 → 八维定义表 → 动作换算”理清整套逻辑，并明白为什么同样是输入 `0.4`，关节有的变成 `0.2 rad`（角度），有的却变成 `2 rad/s`（角速度）。

在深入代码之前，我们先用通俗直白的话了解几个核心术语：

| 术语 | 在本模块中的通俗含义 |
|---|---|
| **策略、策略动作（`a`）** | “策略”是决定机器人动作的大脑规则（通常由神经网络充当）。策略输出的一组纯数字就叫“策略动作”，记作 `a`。它在数学上是无量纲的纯数值，没有物理单位 |
| **向量、列表、索引（Index）** | 向量就是按特定顺序排好的一串数字；八维向量就是装有 8 个数字的列表。**索引**是计算机中的位置编号：在 Python 中数数**从 0 开始**，所以第 1 个数是索引 0，第 4 个数是索引 3（即代码里的 `a[3]`） |
| **关节位置（角度） vs 关节速度** | 对于旋转电机，“位置”指的是转到什么角度，而不是前进距离；“速度”指的是旋转得有多快（角速度），而不是转到了哪里 |
| **物理单位：rad 与 rad/s** | **rad（弧度）**：测量角度的物理单位，半圈（180度）约为 3.14 弧度（`π rad`）。**rad/s（弧度每秒）**：测量旋转快慢的角速度单位。轮子是旋转关节，控制的是轮子每秒转多少弧度，而不是整车在地上每秒跑多少米（m/s） |
| **物理目标（Target）** | 电机底层控制器期望达到的具体角度或速度。物理目标只是电机的期望目标，真实机械由于惯性和外力，不可能在一瞬间就瞬移到位 |
| **默认偏移（Offset）与缩放（Scale）** | **默认偏移**：当策略动作全为 0 时，关节保持的基准目标（例如站立姿态）；**Scale（缩放系数）**：动作每变化 1，物理目标相应改变多少 |
| **裁剪（Clip）** | 数值安全护栏：算出的值若低于下限就拉回下限，高于上限就压回上限。本模块是在算出物理目标之后进行裁剪 |
| **动作项 vs 动作契约** | **动作项（Action Term）**：配置文件中对某一组关节的配置规则；**动作契约（Action Contract）**：把所有动作项按顺序展开、登记成的一张完整权威表（`ActionContract`） |

## 职责与原 PPO 的关系

原版项目 DDT_Lab 使用的是 **PPO** 算法，而我们当前的工作是将其逐步替换为 **SAC** 算法。
无论是 PPO 还是 SAC，它们都是教机器人学习的算法框架（相当于换了学习模式）。但是，**机器人的物理硬件没有变**：原本控制左腿髋关节的输出位置，换了算法后依然必须控制左腿髋关节；原本由角速度驱动的轮子，换了算法后依然必须接收角速度。

E03 从固定原版的 PPO 配置中完整读取并锁定了这套物理语义，供后续 SAC 算法接入时直接继承使用。

需要特别说明的是：**E03 本模块代码是“纯数据”处理**。
这里的“纯数据”意味着：代码只在文本和数字层面解析配置、建立定义表、校验规则、执行公式换算以及生成可读表格；它不需要启动昂贵的 3D 物理引擎（Isaac Lab），也不加载真实的机器人模型。

> [!IMPORTANT]
> **E03 提供动作定义，不单独完成训练算法替换。当前全仓库 SAC 学习与调度代码已实现并有 CPU 验证，E01 也已提供 Isaac 接入入口；真实仿真、GPU 和训练效果尚未验证。**

后续算法模块（产生动作的 Actor 网络、评估动作好坏的 Q 网络、保存交互记录的 Replay Buffer 经验池）都高度依赖 E03：
- 如果轮子速度被误当成角度，后续推导出的动作安全范围就会彻底错误；
- 如果动作向量的顺序排错，或者策略动作与物理目标混为一谈，Q 网络评估的动作就会与机器人实际执行的动作“张冠李戴”，导致算法完全无法收敛。

## 八维输入、输出与数据流

### 固定原版的八个控制位置

下表数据来自实际读取的 PPO 快照配置，并与 `test_contract.py` 中的手写独立参考表完全一致。
请注意：名称带 `*_leg_4` 的关节，在机械结构上其实是**轮子**。

| 人读序号 / 程序索引 | 动作项字段名 | 关节名称 | 控制目标 | 默认偏移 | 缩放 (scale) | 物理单位 | 目标裁剪区间 |
|---|---|---|---|---:|---:|---|---|
| 1 / 0 | `joint_pos_0` | `joint_left_leg_1` | 左腿关节 1 角度 | 0.1 | 0.25 | rad | [-100, 100] |
| 2 / 1 | `joint_pos_1` | `joint_left_leg_2` | 左腿关节 2 角度 | 0.8 | 0.25 | rad | [-100, 100] |
| 3 / 2 | `joint_pos_2` | `joint_left_leg_3` | 左腿关节 3 角度 | -1.5 | 0.25 | rad | [-100, 100] |
| 4 / 3 | `joint_vel_3` | `joint_left_leg_4` | **左轮角速度** | 0.0 | 5.0 | **rad/s** | [-100, 100] |
| 5 / 4 | `joint_pos_4` | `joint_right_leg_1` | 右腿关节 1 角度 | 0.1 | 0.25 | rad | [-100, 100] |
| 6 / 5 | `joint_pos_5` | `joint_right_leg_2` | 右腿关节 2 角度 | 0.8 | 0.25 | rad | [-100, 100] |
| 7 / 6 | `joint_pos_6` | `joint_right_leg_3` | 右腿关节 3 角度 | -1.5 | 0.25 | rad | [-100, 100] |
| 8 / 7 | `joint_vel_7` | `joint_right_leg_4` | **右轮角速度** | 0.0 | 5.0 | **rad/s** | [-100, 100] |

> [!WARNING]
> **绝对不能把前 6 维当成腿、后 2 维当成轮！**
> 仔细观察表格可以发现：控制角度的索引是 `(0, 1, 2, 4, 5, 6)`，控制轮速的索引是 `(3, 7)`。
> 这是因为原版配置是按照“先左侧（3 个腿关节 + 1 个轮子）、后右侧（3 个腿关节 + 1 个轮子）”的顺序依次声明的。
> 这个顺序是由配置代码里的**声明先后次序**决定的，绝不是按关节名字的字母 A-Z 排序，也不是根据字段名末尾的数字自动猜出来的。

### 分清两种不同的输入输出

在阅读代码时，要先分清两个完全不同的业务阶段：

1. **“建表阶段”（程序启动时只做一次）**：
   - **输入**：环境中的动作项配置列表（`ActionTermSpec`），以及机器人的默认关节角度字典、默认关节速度字典（两份“名称 → 数值”的键值表）。
   - **输出**：生成一份全局统一的动作定义表 `ActionContract`。这份表本身不包含任何某一时刻的具体动作数值。
2. **“动作换算阶段”（运行控制时每个周期执行一次）**：
   - **输入**：上述建好的定义表 `ActionContract`，以及策略网络在当前时刻输出的 8 维无量纲动作向量 `a`。
   - **输出**：通过函数 `action_to_targets` 计算出 8 个物理控制目标（6 个为角度 rad，2 个为角速度 rad/s）。
   - **注意**：`action_to_targets` 每次只换算单个机器人的一条动作，不处理包含批量维度的张量（Batch）。

### 模块整体调用数据流

```text
固定原版 PPO 快照中的配置文件（rough_env_cfg / flat_env_cfg / ddt_robot）
  └─ baseline_source.load_baseline_action_contract()
       ├─ read_baseline_file()         : 通过只读 Git 命令提取快照文本并核对树哈希
       ├─ assert_actions_not_modified(): 静态代码守卫，确认没有在运行时篡改动作配置
       ├─ parse_action_terms()         : 用语法树静态解析 rough 中的有序动作项列表
       ├─ parse_init_state()           : 用语法树静态解析 robot 中的默认角度与速度字典
       └─ contract.build_action_contract(): 组装生成完整的动作契约表 ActionContract

外部调用方拿到 ActionContract 后的常见操作：
  ├─ validate_action_contract(contract): 严格校验表格是否符合八维物理规则
  ├─ describe_action_contract(contract): 生成人眼可读的 Markdown 格式表格文本
  └─ action_to_targets(contract, a)    : 把一组具体策略动作 a 换算为物理控制目标
```

请注意，建表（`build_action_contract`）和校验表（`validate_action_contract`）是两个独立的步骤。建表函数不会偷偷自动执行校验，而是由调用方（如命令行入口或单元测试）显式触发校验，确保职责单一分明。

## 按文件、类与函数阅读实际实现

为了方便没有 Python 基础的读者理解，我们先简单解释几条 Python 常见语法：
- **`@dataclass(frozen=True)`（冻结数据类）**：可以把它看作一张设计好的“记录单模板”。`frozen=True` 表示这张单子填好生成之后就是“只读”的，任何代码都不能随手篡改里面的字段值，安全可靠。
- **`Enum`（枚举类）**：表示一组预先写好的、固定有限的选项（比如控制类型只有“角度”和“速度”两种，不能填入其他乱七八糟的词）。
- **`self` 与 `cls`**：写在类内部的函数称为“方法”。`self` 表示当前拿到手里的这一份具体数据记录；`cls` 表示这个数据模板（类）本身。
- **`raise ActionContractError(...)`（抛出异常）**：当程序发现数据违反规则时，主动“亮红牌”紧急停止运行，并把发现的错误原因打印出来。
- **返回 `None`**：如果一个校验函数的职责只是“把关”，在没发现任何毛病时它就会正常结束并返回 `None`（表示“顺利过关，一切正常”）。

### `contract.py`：定义契约、构建表格、校验与目标换算

[contract.py](contract.py) 是本模块最核心的逻辑文件。它不读取硬盘文件，也不启动仿真；其中的所有函数都是纯计算逻辑，绝不会修改外部输入的数据。

| 类或常量 | 字段与设计职责 |
|---|---|
| `ActionContractError` | 动作契约专用的异常类型，继承自 Python 内置的 `ValueError`。当建表或校验失败时抛出，能把发现的所有问题一次性全部列出，避免“改一个报一个” |
| `ControlType` | 枚举类，规定控制类型的固定选项：`POSITION` 对应位置控制（配置类名 `JointPositionActionCfg`，单位 `rad`）；`VELOCITY` 对应速度控制（配置类名 `JointVelocityActionCfg`，单位 `rad/s`） |
| `TITA_ACTION_LAYOUT` | 固定的八组 `(关节名称, 控制类型)` 元组模板。**只固定顺序和控制类型**，不写死具体的默认值或 scale（具体数值动态从配置读取，再由测试逐项核对） |
| `ActionTermSpec` | 存储一条动作项配置的数据类：包含字段名 `term_name`、控制类型 `control_type`、精确关节名列表 `joint_names`、缩放系数 `scale`、是否使用模型默认偏移 `use_default_offset`（默认 True）、手动固定偏移 `offset`、裁剪规则 `clip`，以及是否保持顺序 `preserve_order` |
| `ActionEntry` | 展开后的动作定义表单行记录：包含索引 `index`（0~7）、动作项名 `term_name`、关节名 `joint_name`、控制类型 `control_type`、物理单位 `unit`、零动作基准目标 `default_target`、缩放系数 `scale`，以及物理裁剪上下限 `clip_low`、`clip_high`（默认负无穷到正无穷） |
| `ActionContract` | 封装整张动作表的只读数据类，核心字段为有序的 `entries`。提供多种按列取值的便捷属性，方便下游（如 E04）直接转换成 PyTorch 张量，无需下游再拼一遍顺序 |

各函数与方法的功能清单如下：

| 函数或方法 | 输入参数、输出与职责 | 为什么这样设计 / 边界限制 |
|---|---|---|
| `ControlType.cfg_class_name` | 属性，返回该类型对应的配置类名字符串（如 `"JointPositionActionCfg"`） | 供解析器识别配置类型 |
| `ControlType.unit` | 属性，返回该类型的标准物理单位（`"rad"` 或 `"rad/s"`） | 确保单位与类型永远绑定一致 |
| `ControlType.from_cfg_class_name(name)` | 输入配置类名字符串，返回枚举项；遇到不支持的类名（如力矩控制）抛出 `ActionContractError` | 严格防范非法配置进入系统 |
| `ActionContract.__len__()` | 允许使用 `len(contract)`，返回表格行数 | 原版 TITA 固定为 8 行 |
| `ActionContract.joint_names` | 属性，按行返回所有 8 个关节名称的元组 | 顺序与动作向量严格一致 |
| `ActionContract.scales` | 属性，按行返回所有 8 个缩放系数的元组 | 供下游批量换算时提取系数向量 |
| `ActionContract.default_targets` | 属性，按行返回所有 8 个默认基准目标的元组 | 零动作时的基准值，物理单位视行而定 |
| `ActionContract.indices_of(control_type)` | 输入控制类型（如 `VELOCITY`），返回匹配的索引元组 | 例如查询速度项，返回 `(3, 7)` |
| `resolve_joint_values(patterns, joint_names)` | 输入“正则规则 → 数值”字典与目标关节名，返回“具体关节名 → 浮点数值”字典 | 使用完整匹配（`re.fullmatch`）。若某个关节没有匹配项，或同时命中多条正则规则，立刻报错拒绝 |
| `_resolve_clip(clip, joint)` | 内部辅助函数（下划线开头提示内部使用）。输入裁剪规则字典与单个关节名，返回裁剪上下限 `(low, high)` | 未配置或未命中规则时默认返回 `(-inf, inf)`（表示不限制）；若命中多条规则则报错 |
| `build_action_contract(terms, default_joint_pos, default_joint_vel)` | 主建表函数：输入动作项列表、默认角度字典、默认速度字典，逐行分配连续索引并提取偏移，组装返回 `ActionContract` | 拒绝包含多关节但 `preserve_order=False` 的项；不自带 TITA 布局校验（需显式调用校验函数） |
| `validate_action_contract(contract, expected_layout=TITA_ACTION_LAYOUT)` | 核心校验函数：检查索引连续性、关节重名、单位匹配、数值有限且非零、裁剪上下限顺序；再逐项比对期望布局 | 逐个索引严格对比。如果所有关节都在但顺序乱了，或者按字母排序了，都会被立即拦截拒绝 |
| `action_to_targets(contract, action)` | 换算函数：输入定义表与单条 8 维策略动作 `a`，输出换算后的 8 维物理目标元组 | 检查维度是否为 8、排除非有限数值（如 NaN 或无穷大）。不负责计算电机力矩 |
| `describe_action_contract(contract)` | 格式化函数：输入动作定义表，返回整齐排版的 Markdown 表格字符串 | 供命令行或日志打印核对，自身不执行 print |

### `baseline_source.py`：静态提取原版配置，无需安装仿真器

[baseline_source.py](baseline_source.py) 使用了 Python 标准库自带的 `ast`（抽象语法树，Abstract Syntax Tree）模块。
所谓**静态解析**，就像我们直接“阅读代码文本的句子结构”，在不需要真正运行该文件、也不需要导入外部重型库（如 Isaac Sim / Isaac Lab）的前提下，把类定义、参数赋值精准抓取出来。

> [!NOTE]
> **什么是字面量（Literal）？**
> 字面量是指在代码中直接写出的固定数值，比如 `0.25`、`True`、`["joint_left_leg_1"]`。如果配置中写的是复杂的函数计算或动态变量，静态解析器就会主动报错拒绝，绝不胡乱猜测。

| 常量名称 | 取值与作用 |
|---|---|

## 关键计算：从定义表走到物理目标

本节将带领读者对照核心源码，一步步看清数据是如何流动的。

### 1. 为什么必须严格保留声明顺序？

在解析配置时，`parse_action_terms` 会在类结构中执行如下循环：

```python
for stmt in cls.body:
```

`cls.body` 是 Python 语法分析器按照**源代码书写的自然先后顺序**排布的语句列表。解析器不会自作主张对字段重新排序，写在第一行的项就在第一个。

紧接着，建表函数 `build_action_contract` 展开两层循环：

```python
for term in terms:
    for joint in term.joint_names:
```

在为每一个关节创建 `ActionEntry` 记录行时，程序决定该关节索引编号的代码非常简单纯粹：

```python
index=len(entries),
```

`len(entries)` 代表“当前列表中已经积攒了多少行记录”。
第一行记录生成时，列表长度为 0，所以索引就是 `0`；第二行生成时，列表已有 1 项，所以索引就是 `1`……以此类推，索引严密递增到 `7`。

这就像一个行李分拣传送带：每一个动作项按照出厂配置声明的先后顺序依次进入传送带，分配到 `0, 1, 2, ... 7` 的固定篮子里。
如果有人把关节按照英文字母 A 到 Z 重新排序，篮子里的物品就会全部分配错位，导致原本给轮子的信号发送给了髋关节。

在校验函数 `validate_action_contract` 中，也是按照这个原则开展铁面检查：

```python
for position, (e, (name, ctype)) in enumerate(zip(entries, expected_layout)):
```

`zip` 会把实际生成的每一行与标准期望的每一行成对绑定，`position` 记录当前是第几个位置。代码在每一个位置上都严格核对关节名字和控制类型。只要位置错了一位，即使 8 个关节一个没落，校验也会当场报错报警。

### 2. 默认偏移是怎样精准选取的？

当策略网络输出 0 动作时，关节应该呆在什么位置？
在 `build_action_contract` 中，有这样一段决定基准目标的关键逻辑：

```python
if not term.use_default_offset:
    offset = float(term.offset)
elif term.control_type is ControlType.POSITION:
    offset = resolve_joint_values(default_joint_pos, [joint])[joint]
else:
    # 速度项的默认偏移是“默认关节速度”，不是默认关节角。轮子关节的默认角恰好也是 0，
    # 若误用角度，在原版数值上看不出错，换一个轮子初始角就会让零动作变成持续转动。
    offset = resolve_joint_values(default_joint_vel, [joint])[joint]
```

我们逐行拆解这段逻辑的妙处：
1. `if not term.use_default_offset`：如果配置里明确要求“不使用机器人的模型默认值”，那就直接采用配置里写死的固定常数 `term.offset`。
2. `elif term.control_type is ControlType.POSITION`：如果是位置控制（腿部关节），代码就从**默认关节角度表**（`default_joint_pos`）中查找该关节的角度值（例如 0.1、0.8、-1.5 rad）。
3. `else`：剩下的是速度控制（轮子关节），代码就会走到这个分支，**严格从默认关节速度表（`default_joint_vel`）中提取默认速度**（0.0 rad/s）。

> [!CAUTION]
> **警惕“巧合的零值”陷阱！**
> 在原版 TITA 机器人的配置中，轮子的初始角度恰好是 0.0，初始速度也恰好是 0.0。
> 如果代码编写者粗心大意，把速度项也写成了去查默认角度表，程序在原版配置下测试竟然完全能跑通，表面上看起来毫无破绽！
> 但是，一旦未来有人把机器人的轮子初始摆放朝向改成 0.7 弧度，这种隐蔽的错误就会瞬间暴雷：当策略大脑给出全 0 动作想要静止站立时，轮子却会误把 0.7 弧度当成速度目标，以 0.7 rad/s 的速度一直狂转！
> 这就是为什么代码中必须显式区分 `POSITION` 和 `VELOCITY`，也是为什么测试用例中专门人工构造了“轮子角度为 0.7、轮速为 0”的极端情况进行针对性测试。

### 3. 先缩放、加偏移，最后执行物理裁剪

`action_to_targets` 函数负责将某一时刻的无量纲动作 `a` 换算为真实的电机控制目标。
核心换算代码只有短短两行：

```python
target = a * e.scale + e.default_target
targets.append(min(max(target, e.clip_low), e.clip_high))
```

这两行的运算顺序非常讲究：
1. **第一行（物理换算）**：策略网络给出的动作 `a` 是一个抽象的无量纲数值。首先把它乘以缩放系数 `e.scale`，再加上默认基准值 `e.default_target`。直到这一刻，抽象的数字才真正蜕变为具有物理意义的角度（rad）或角速度（rad/s）。
2. **第二行（安全裁剪）**：`max(target, e.clip_low)` 确保数值不会跌破下限，`min(..., e.clip_high)` 确保数值不会冲破上限。算出的目标值被安全装入结果列表。

数学表达公式如下：
- **腿部关节角度目标**：$q^* = \text{clip}(q_0 + 0.25 \times a)$（其中 $q_0$ 为默认角度，$0.25$ 为 scale）
- **轮子转速目标**：$\omega^* = \text{clip}(0 + 5.0 \times a)$（其中 $0$ 为默认角速度，$5.0$ 为 scale）

> [!NOTE]
> 原版配置中的物理裁剪范围是 `[-100, 100]`。在正常动作范围内，算出的角度或速度绝不会达到 ±100，所以这个裁剪在平时不会被触发。它是物理层面的宽泛安全网，**绝不代表后续 SAC 策略动作的输出边界**（SAC 的具体边界将由后续的 E04 模块负责推导）。

测试用例 `RuleTest.test_clip_applies_to_physical_target` 专门设计了一个精巧的人工案例证明运算顺序：
假设偏移量为 0.8、scale 为 0.25、裁剪区间设为 `[-1, 1]`。当策略输入动作为 1 时：
- **正确顺序（现行代码）**：先算物理目标 $0.8 + 0.25 \times 1 = 1.05$，然后裁剪到 `[-1, 1]`，最终得到安全输出 `1.0`。
- **错误顺序（颠倒逻辑）**：如果先把动作 1 裁剪在 `[-1, 1]` 内（依然是 1），再算物理目标，就会得到超标的 `1.05`。
测试成功证明了：必须先换算成物理量，再施加物理裁剪。

### 4. 用三个真实验收案例贯穿理解

我们用三个具体的动作输入，彻底串联起整套换算逻辑：

```text
案例一（零动作输入）：
策略动作 a：    [0,   0,   0,    0,   0,   0,   0,    0]
物理目标 target: [0.1, 0.8, -1.5, 0.0, 0.1, 0.8, -1.5, 0.0]

案例二（仅改动左腿第一维）：
策略动作 a：    [0.4, 0,   0,    0,   0,   0,   0,    0]
物理目标 target: [0.2, 0.8, -1.5, 0.0, 0.1, 0.8, -1.5, 0.0]

案例三（仅改动左轮那一维）：
策略动作 a：    [0,   0,   0,    0.4, 0,   0,   0,    0]
物理目标 target: [0.1, 0.8, -1.5, 2.0, 0.1, 0.8, -1.5, 0.0]
```

- **案例一（零动作）**：每个维度的动作值都是 0，乘以 scale 后都是 0，因此最终输出全部等于基准默认偏移。腿部维持默认站立角度，轮子维持零转速。
- **案例二（左腿微动）**：只有第 1 个数是 0.4，对应左腿第 1 关节：`0.1 + 0.25 × 0.4 = 0.2 rad`。关节目标从 0.1 rad 提升到了 0.2 rad（增加了 0.1 rad），其余 7 个关节全部维持默认值不变。
- **案例三（左轮加速）**：只有第 4 个数是 0.4（程序索引 3），对应左轮关节：`0 + 5.0 × 0.4 = 2.0 rad/s`。轮子目标变成了以每秒 2 弧度的角速度旋转，其余 7 个关节维持默认值不变。请注意，这里的 2 是轮子自身的旋转角速度（rad/s），不是整车在地面上奔跑的米每秒（m/s）。

#### 深度思考：为什么“零动作”不等于“电机不出力”？

初学者常常产生一种直觉误解：“既然策略输出的动作全为 0，那电机是不是就断电、彻底不出力了？”
**事实恰恰相反！零动作绝不等于零力矩。**

底层的电机是由 PD 控制器驱动的：
- **腿部关节**：原版配置中位置纠正刚度系数高达 `stiffness = 60`，阻尼系数 `damping = 1.5`。当动作为 0 时，我们给电机的物理目标是“维持站立角度（如 0.1、0.8、-1.5 rad）”。如果机器人受到重力下沉或者被外力推搡，导致实际关节角度偏离了站立角度，底层电机就会爆发大力矩死死顶住，努力将身体支撑回原位！
- **轮子关节**：原版配置中刚度系数为 0（`stiffness = 0`），阻尼系数为 `damping = 0.5`。当轮速目标设为 0 rad/s 时，如果此时机器人由于惯性轮子还在飞转，电机就会产生强烈的反向阻尼力矩，相当于**一脚踩下刹车**，强行把轮速拉停到 0！

因此，“零动作”代表的是“请保持默认站立姿态，并刹停轮子”，而不是放任不管的零力矩。

### 5. 为什么本定义表是 SAC 算法的基石？

后续我们将全面展开 SAC 算法的构建，而 E03 定义表是整个算法大厦的地基：
1. **反推策略动作范围（E04 动作边界模块）**：
   SAC 网络需要知道自己输出的动作 `a` 的合理取值范围。我们可以利用本模块的公式进行逆运算：
   $$a = \frac{q^* - q_0}{\text{scale}}$$
   根据机械允许的最大/最小安全角度 $q^*$，反推出策略输出 $a$ 的极限边界。如果把轮速当成角度，或者弄错了 scale 和基准值，反推出来的动作边界就会荒诞不经。
2. **统一强化学习算法的坐标系（D01 经验池与 Q 网络）**：
   在强化学习中，策略大脑输出的动作是无量纲的 $a$（比如 0.4）。我们在经验回放池里记录的、在 Q 价值网络里用来评估“这个动作好不好”的，都必须是统一的策略动作坐标 $a$。
   如果执行器在底层用的是换算后的物理值 `2.0 rad/s`，而经验池和网络如果混乱地把 2.0 当作策略动作存进去，评估与执行就会彻底错乱，导致整个训练崩溃发散。

### 常见问题排查速查表

如果在后续开发或使用中遇到疑惑，可参考下表快速定位：

| 遇到现象或报错 | 排查方向与定位点 |
|---|---|
| **左右腿搞反了，或者关节对应错了** | 对照八维定义表、`TITA_ACTION_LAYOUT` 以及 `parse_action_terms` 的声明顺序。**绝对不要试图通过“按字母排序”来修 bug** |
| **轮子转速异常暴走，或者数值大得离谱** | 检查索引是否为 3 或 7；检查控制类型是否为速度控制；检查 scale 是否为 5.0。注意分清：策略动作值 0.4、物理角速度 2 rad/s、以及整车在地面奔跑的实际线速度 |
| **输入全 0 动作后，机器人姿态不是预期的站立姿态** | 检查 `build_action_contract` 中的偏移选择逻辑：轮子看速度表 `joint_vel`，腿部看角度表 `joint_pos`。同时记住：零动作只下达期望目标，机械能否站稳还受物理约束和电机力矩影响 |
| **报错提示没有匹配项，或同时命中多个配置规则** | 检查传递给 `resolve_joint_values` 的正则表达式字典。规则必须严丝合缝，每个关节必须恰好命中一条规则 |
| **报错提示动作维数不对，或包含 NaN** | 检查传入的动作列表长度是否严格为 8；检查策略网络输出中是否产生了无效数值（NaN / 无穷大） |
| **测试出现 `skipped` 或 Git 读取失败** | 检查本地是否安装了 git，并执行 `git fetch origin baseline/ppo` 获取快照提交 |
| **在外部脚本中 `import contract` 提示模块找不到** | 检查当前目录是否已加入 Python 的搜索路径列表 `sys.path` |
